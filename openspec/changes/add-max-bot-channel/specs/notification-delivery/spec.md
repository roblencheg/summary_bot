## MODIFIED Requirements

### Requirement: Срок доставки алерта
Система SHALL отправлять одиночный алерт в пределах 60 секунд от получения сообщения системой при штатной работе и MUST отдельно измерять задержку поступления сообщения из канала-источника (Telegram или MAX).

#### Scenario: Замер задержек
- **WHEN** алерт доставлен
- **THEN** в журнале сохранены время сообщения в канале-источнике, время получения, время анализа и время отправки

### Requirement: Повторы и ограничения канала доставки
Система SHALL повторять неуспешные отправки с экспоненциальным backoff и jitter, соблюдать собственные ограничения скорости API того канала, через который идёт отправка (Telegram или MAX), и MUST NOT повторять бесконечно при блокировке бота получателем.

#### Scenario: Пользователь заблокировал бота
- **WHEN** API канала отвечает кодом «бот заблокирован получателем»
- **THEN** задание получает статус «заблокировано получателем» без повторов, привязка получателя к этому каналу помечается блокированной в интерфейсе, второй канал (если привязан) не затрагивается

#### Scenario: Rate limit
- **WHEN** API канала отвечает ограничением скорости с указанием времени повтора
- **THEN** следующая попытка этого задания выполняется не раньше указанного времени

#### Scenario: Исчерпание попыток
- **WHEN** после 5 попыток сохраняется серверная ошибка канала
- **THEN** задание получает статус «ошибка», видно в журнале с указанием канала и доступно для ручного повтора

### Requirement: Неопределённый результат
Система SHALL помечать попытку как «результат неизвестен» при сетевом обрыве после отправки запроса к API канала и повторять её с пометкой «возможен дубль»; система MUST NOT обещать exactly-once доставку и SHALL считать успехом принятие сообщения API канала, а не прочтение.

#### Scenario: Таймаут ответа канала
- **WHEN** запрос на отправку сообщения ушёл в Telegram или в MAX, но ответ не получен
- **THEN** попытка записана как «результат неизвестен», повтор содержит пометку о возможном дубле

### Requirement: Неактивированный получатель
Система MUST NOT отмечать доставку успешной получателю, не активировавшему бота того канала, в который адресовано задание.

#### Scenario: Саммари неактивированному в канале
- **WHEN** наступает время саммари по чатам канала, в котором получатель не привязан
- **THEN** задание этого канала получает статус «получатель не активировал бота», а не «доставлено»; задания по другому каналу, если получатель там активен, идут своим ходом

### Requirement: Выбор канала доставки
Система SHALL определять канал (Telegram или MAX) для каждого задания доставки в момент постановки в очередь: для алерта и обновления инцидента — канал чата, к которому относится инцидент; для периодического отчёта — по каждому каналу, где у получателя за период есть подписанные чаты, отдельным заданием; для меню, тестового и технического уведомления, не привязанных к чату, — по одному заданию на каждый канал, в котором получатель сейчас активен. Система MUST выбирать клиента и идентификатор получателя соответствующего канала при обработке задания и MUST NOT отправлять rich-форматированное сообщение (таблицы, сворачиваемые блоки) в канал MAX.

#### Scenario: Алерт MAX-чата
- **WHEN** в MAX-чате возникает инцидент, подписанный получатель привязан и к Telegram, и к MAX
- **THEN** алерт отправляется только через MAX, Telegram не используется для этого задания

#### Scenario: Получатель с чатами в обоих каналах
- **WHEN** у получателя есть подписанные чаты и в Telegram, и в MAX на один и тот же период саммари
- **THEN** за период ставятся два задания — одно с содержимым Telegram-чатов в Telegram, другое с содержимым MAX-чатов в MAX

#### Scenario: Меню одновременно в двух каналах
- **WHEN** администратор отправляет получателю, активному и в Telegram, и в MAX, меню бота
- **THEN** ставятся два задания — по одному на каждый активный канал
