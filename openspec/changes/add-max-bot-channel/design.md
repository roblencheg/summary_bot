## Контекст

Сейчас Telegram жёстко вплетён в домен: у `recipients` поля называются `telegram_user_id`/`telegram_username`, типы апдейтов (`TgMessage`, `TgUpdate`, `TgChat`) специфичны для Bot API, deep-link для привязки — `t.me/<bot>?start=<код>`, доставка и её ретраи/rate-limit заточены под коды ошибок Telegram (403/429/`bad_request`), rich-отправка — Bot API 10.1 (`rich_message.html`), а канал как понятие в системе не существует — он один и подразумевается.

MAX Bot API (проверено по официальной OpenAPI-схеме `max-messenger/api-schema` и `dev.max.ru/docs-api`) структурно близок к Telegram, но не идентичен:
- База `https://platform-api2.max.ru/`, токен — в заголовке `Authorization: <access_token>` (не в URL, как у Telegram).
- `GET /updates`: `marker` (int64, аналог `offset`), `timeout` (0–90, по умолчанию 30), `limit` (1–1000), `types`.
- Основные типы апдейтов: `message_created`, `message_edited`, `message_removed`, `bot_added`, `bot_removed`, `bot_started`, `message_callback`, `chat_title_changed`, `bot_admin_permissions_changed`. `bot_started` несёt поле `payload` (строка, до 128 символов) — это прямой аналог параметра `/start <код>` у Telegram: пользователь жмёт ссылку с параметром, бот получает его в `payload`.
- `POST /messages`: `text` (до 4000 символов), `attachments`, `format: markdown|html`, `notify`; `PUT /messages` — редактирование, но у MAX есть **лимит в 24 часа** на редактирование сообщения (у Telegram такого лимита нет — это ограничивает вечное перерисовывание меню через `editMessageText`, которое сейчас используется для Telegram).
- `POST /subscriptions` — управление вебхуком; **в доступной документации не нашли описания проверки подписи/секрета входящего запроса** (у Telegram — заголовок `X-Telegram-Bot-Api-Secret-Token`, сверяемый `timingSafeEqual`). Это риск, см. ниже.
- `POST /answers` — ответ на нажатие кнопки (аналог `answerCallbackQuery`), кнопки `CallbackButton{text, payload до 1024 символов}` — запас больше, чем 64 байта у Telegram `callback_data`.
- Rich-сообщений уровня Telegram Bot API 10.1 (таблицы, сворачиваемые блоки) у MAX нет; поддерживается только базовый `markdown`/`html` (без спойлеров, цитат, кастомных эмодзи).
- Деплой в prod сейчас недостижим снаружи (тот же факт, что уже задокументирован для Telegram в `docs/project.md` → «Симптом → причина»), поэтому webhook для MAX в prod так же не сработает — остаётся long polling, хотя сама MAX-документация называет polling режимом «только для разработки».

## Цели / Не-цели

**Цели:**
- Параллельный MAX-контур: сбор MAX-групп, анализ, инциденты, доставка — работает точно так же, как Telegram, без деградации существующего Telegram-поведения.
- Получатель может быть одновременно привязан к Telegram и к MAX; контент каждого чата/инцидента идёт в канал этого чата; периодический отчёт собирается отдельно по каждому каналу получателя.
- Минимальное расхождение с существующим кодом: копируем структуру `client → webhook route → ingestion → intake worker → bot-command-service → callback-router → delivery-service`, а не придумываем новую.

**Не-цели:**
- Не переносим и не дублируем существующие Telegram-чаты в MAX и наоборот — у чата один канал на всю жизнь.
- Не воспроизводим rich-HTML (таблицы/сворачиваемые блоки) для MAX — там, где Telegram использует `sendRichMessage`, MAX всегда получает обычный текст.
- Не вводим общую абстракцию «любой мессенджер» сверх того, что нужно для двух каналов — три и более канала не рассматриваются, это не универсальный плагинный слой.
- Не меняем формат уже отправленных Telegram-уведомлений и схему их таблиц сверх добавления колонки `channel`.

## Решения

### 1. Признак канала у чата, а не у подписки

`chats` получает колонку `channel TEXT NOT NULL DEFAULT 'telegram' CHECK (channel IN ('telegram','max'))`. Значение выставляется один раз — при первом событии (`my_chat_member`/`bot_added`) тем ботом, который увидел группу, и дальше не меняется. Это проще, чем опознавать канал по `chat_id` на каждый запрос, и соответствует факту: группа физически существует в одном мессенджере.

Альтернатива — хранить канал в `delivery_jobs` без привязки к чату и выбирать его по идентификатору получателя — отклонена: для контента, завязанного на чат (алерт, обновление инцидента), канал обязан совпадать с каналом чата, а не с тем, к какому боту получатель оказался привязан первым.

### 2. Признак канала у получателя — параллельные колонки, а не отдельная таблица

По образцу уже существующих `telegram_user_id`/`telegram_username`/`status`/`activated_at`/`blocked_at`/`menu_message_id` добавляются зеркальные `max_user_id`/`max_username`/`max_status`/`max_activated_at`/`max_blocked_at`/`max_menu_message_id`. Рассматривался вариант отдельной таблицы `recipient_channels(recipient_id, channel, external_id, username, status, ...)` — он чище при N каналах, но здесь N=2 и не растёт: продукт ориентирован на российские мессенджеры поддержки, третий канал в обозримой перспективе не планируется. Параллельные колонки дешевле по коду (репозиторий и так пишет явные SQL-методы под Telegram — `bind`, `resetBinding`, `markBlocked`, `setMenuMessageId` — для MAX симметрично добавляются такие же методы с суффиксом канала), без JOIN на каждый список получателей. Если канал понадобится третий — тогда и имеет смысл сворачивать в таблицу, не раньше.

Общие для получателя настройки (`name`, `alert_categories`, `alert_min_severity`, `summary_day`/`summary_night`, `is_tech_admin`) остаются общими — это предпочтения человека, а не канала.

Админский переключатель «включить/отключить получателя» (сейчас — значение `disabled` в колонке `status`) логически относится к получателю целиком, а не к одному каналу: при отключении получателя оба канала (`status` и `max_status`) переводятся в `disabled`; при включении каждый канал восстанавливается в `active`, если у него есть привязанный `*_user_id`, иначе — в `pending`. Это сохраняет текущее поведение для Telegram-only получателей бит-в-бит.

### 3. Один код привязки — один канал

Код/ссылка привязки (`binding_codes`) выдаётся на конкретный канал: администратор в карточке получателя жмёт «Привязать Telegram» или «Привязать MAX» отдельно, получает свою ссылку на свой канал. Таблица `binding_codes` получает колонку `channel`, `useCode`/`bindByCode` проверяют и пишут только одноимённый `*_user_id`/`*_status`. Deep-link для MAX — по аналогии с Telegram (`t.me/<bot>?start=<код>` → `payload` в `bot_started`); точный формат пользовательской ссылки (`max.ru/...` или внутри MasterBot) документация не фиксирует явно — на этапе реализации проверить актуальный формат у `@MasterBot`, до тех пор код можно сообщать текстом для ручного ввода `/start <код>` в диалоге с ботом, без кликабельной ссылки, если формат ссылки не подтвердится.

Слияние дублей при привязке (если под одним Telegram-ID или MAX-ID уже есть другой получатель) работает как сейчас — но проверка конфликта идёт по колонкам того канала, на который выдан код, не трогая второй канал слитых записей.

### 4. Доставка: `channel` в `delivery_jobs`, выбор клиента в `DeliveryService`

`delivery_jobs`/`delivery_attempts` получают колонку `channel`. Простановка значения — в момент постановки задания в очередь, а не при обработке:
- `alert`/`incident_update` — канал инцидента (= канал его чата).
- `summary` — отдельное задание **на каждый канал**, где у получателя за период есть подписанные чаты: `SummaryScheduler`/`ReportService` формирует `reports` не одной строкой на получателя за период, а одной строкой **на пару (получатель, канал)**, собирая `chat_period_digests` только по чатам своего канала. У получателя без MAX-подписок это не меняет поведение — одна запись, один канал, как сейчас.
- `menu`/`test`/`tech` — не привязаны к чату, поэтому ставятся по одному заданию на каждый канал, где получатель сейчас `active` (если активен в обоих — два задания, если только в одном — одно).
- `on_demand` — канал берётся из того бота, в котором пришло нажатие `menu:now` (`cb` несёт канал неявно — его обрабатывает конкретный `CallbackRouter`/клиент).

`DeliveryService.process` при выборе транспорта смотрит `job.channel`: `telegram` → текущий путь (`bot.requireClient()`, `telegramUserId`), `max` → новый `maxBot.requireClient()`/`maxUserId`. Проверки «не активирован»/«заблокирован» делаются по статусу своего канала (`status`/`max_status`), а не общие. Rich-попытка (`sendRichMessage`) выполняется только когда `job.channel === 'telegram'` — для MAX сразу идут `content.parts` обычным текстом.

Классификация ошибок (`blocked`/`rate_limit`/`bad_request`/…) переносится в отдельный `MaxError`/`MaxErrorKind` по образцу `TelegramError`, т.к. коды и структура ответа MAX не идентичны Telegram (это выяснится точно при реализации по реальным ответам API — закладываем классификацию по аналогии: 403 → `blocked`, 429 → `rate_limit`, прочие 4xx → `bad_request`).

### 5. Приём MAX зеркалит Telegram, без обобщения ingestion-пайплайна в общий код

`max-ingestion` — отдельная таблица `max_updates` (не общая с `telegram_updates`), отдельный `MaxIntakeService`/`MaxIngestionService`, отдельный воркер-цикл (как `polling`/`intake` сейчас, только второй экземпляр с клиентом MAX). Для `onMessage`/`onEdit`/`onMembership` бизнес-логика (идемпотентность по `chat_id+message_id`, детект значимой правки, роли по списку ID сотрудников, пробелы сбора) переиспользуется как есть — она уже оперирует абстрактными `chat_id`/`message_id`/текстом, а не Telegram-типами; меняется только слой, который достаёт эти поля из `MaxUpdate` вместо `TgUpdate`.

Решение не обобщать транспорт (`ingestion-service`/`intake-service`) под общий интерфейс «любой мессенджер» — ради простоты и явности: два похожих, но самостоятельных файла дешевле читать и чинить, чем один файл с ветвлениями по каналу внутри каждого метода. Если в будущем появится третий канал — тогда и выделять общий интерфейс, не раньше (см. «Не-цели»).

### 6. Webhook или polling для MAX

По умолчанию `MAX_MODE=polling` в prod (как и Telegram — домен деплоя не достижим снаружи) и `off` в dev. `webhook` поддержать в клиенте как опцию на будущее, но не включать по умолчанию — ещё и потому, что проверка подлинности webhook-запроса MAX не задокументирована однозначно (см. риски).

## Риски / Компромиссы

- **[Подпись webhook MAX не задокументирована]** → используем `polling` по умолчанию везде, как и для Telegram; webhook для MAX не включать, пока не подтверждён механизм проверки запроса (иначе любой внешний POST на `/api/max/webhook` будет приниматься как настоящий апдейт).
- **[Точный формат deep-link для привязки через MAX]** → подтверждён официальной OpenAPI-схемой (github.com/max-messenger/api-schema, README.mdx, «Deep linking»): `https://max.ru/<botName>?start=<payload>`. Реализовано в `recipient-service.ts` (`issueCode`) по аналогии с Telegram; код также можно ввести текстом `/start <код>` в диалоге (`MaxCommandService.handlePrivate`) как резервный путь.
- **[MAX ограничивает редактирование сообщений 24 часами]** → переиспользование меню через `editMessageText` (сейчас используется для Telegram, чтобы не слать новое сообщение) для MAX работает только в первые сутки после отправки; после — `pinMenu`/обновление меню должно отправлять новое сообщение и перезакреплять его, а не падать молча.
- **[Разделение периодического отчёта по каналам меняет кардинальность `reports`]** → было 1 запись на (получатель, период), станет 1 на (получатель, канал, период); если получатель подписан на чаты только одного канала — поведение и количество сообщений не меняются, рост кардинальности есть только у получателей с чатами в обоих каналах одновременно.
- **[Коды ошибок и rate-limit MAX не идентичны Telegram]** → классификация ошибок MAX закладывается по аналогии (403/429/4xx/5xx), уточняется по факту реальных ответов API на этапе реализации; до уточнения доставка в MAX не должна считаться менее надёжной, чем в Telegram, за счёт тех же принципов (backoff, journal, ручной повтор).

## Открытые вопросы

- Механизм проверки подлинности webhook-запроса MAX (секрет, подпись, заголовок) — в открытой документации не нашли; до уточнения вебхук не включаем.
- Полный и окончательный список типов обновлений (`update_type`) и структура ответа при ошибке (аналог `{ok, error_code, description}` у Telegram) — заложенный список и классификация ошибок проверяются по факту при подключении реального токена.
