## Контекст

Алерт и саммари уже содержат почти все нужные данные: автора, чат, суть обращения (`summary` из анализа), заголовок инцидента, статусы обращений и счётчики из SQL. Проблема в подаче. Алерт начинается с уровня серьёзности, суть видна только в цитате клиента. В саммари все блоки одного веса, и общая оценка обстановки нигде не сформулирована. Сводка «Что сейчас происходит» использует тот же `ReportService.render`, поэтому новый формат получит автоматически.

Ограничения остаются прежними: числа считает SQL; утверждения AI без валидных оснований отбрасываются; в Telegram — маскирование и разбиение на части по 4096 символов (`splitMessage`); схема БД не меняется.

## Цели / Не-цели

**Цели:**
- Алерт: «кто · что · где» в первых трёх строках и признак ответа поддержки.
- Саммари: вывод об обстановке на первом экране (светофор, «Требует решения»), подробности ниже без сокращений.
- Оценка обстановки детерминирована и работает без AI.

**Не-цели:**
- Не меняем правила создания и порогов инцидентов, cooldown, адресацию и права.
- Не меняем веб-интерфейс: полный текст отчёта там уже показывается как есть.
- Не вводим настраиваемые пороги светофора: правило фиксированное, при необходимости вынесем в настройки отдельным изменением.

## Решения

1. **Светофор считает код, а не AI.** Новая чистая функция `server/domain/situation.ts`: `chatSituation(digest) → { level: 'red'|'yellow'|'green'|'none', reasons: string[] }`. Работает только с данными дайджеста: `incidents` (уровень, статус), `spikes`, статусы обращений (`no_reply`), распределение тона, `stats.messages`. Общий цвет — худший среди чатов.
   Альтернатива — просить модель оценить обстановку. Отклонена: оценка была бы невоспроизводимой, без AI блок пропадал бы, и вывод нельзя сверить с БД.

2. **«Требует решения» собирается из уже посчитанных данных дайджестов.** Источники: `content.incidents` (активные, статусы `new`/`seen`) и `content.requests` со статусом `no_reply`. Обращение без ответа не попадает в список второй раз, если у того же автора в этом чате уже есть активный инцидент. Сопоставляем по имени автора: так дубль не появится, даже если инцидент собран из нескольких обращений. Для этого в `DigestContent.incidents` добавляются `authorName`, `link`, `firstMessageAt` и `staffReplied` — это JSON дайджеста, в схеме БД ничего не меняется. Сортировка: уровень → время. В Telegram показываем до 15 пунктов с пометкой «ещё N — в веб-интерфейсе».

3. **Итоговая фраза по чату (`headline`)** — новое поле ответа модели в дайджесте: одно утверждение со списком `evidence_message_ids`. Валидируется так же, как остальные утверждения; без оснований не показывается. Версия промпта `digest-v3`. В старых дайджестах (`digest-v2`) поля нет, и раздел выводится без фразы.
   Альтернатива — брать первое утверждение из `overview`. Отклонена: `overview` описывает события, а не состояние.

4. **Признак ответа поддержки в алерте** — новый метод `IncidentRepository.staffReplied(incidentId)`: `EXISTS` по сообщениям сотрудника (`is_staff = 1`) того же чата, которые отвечают на сообщение инцидента (reply) или отправлены после первого сообщения инцидента. Логика та же, что в `chatPeriodRequests`, но без окна ожидания: для руководителя важно, отвечали ли вообще. Если `chats.staffConfigured(chatId)` = false, выводим «ответы не отслеживаются». Каждый алерт добавляет один SQL-запрос (≈160 мс) — это укладывается в срок доставки.

5. **Главная категория в первой строке алерта.** Берём первую категорию инцидента по приоритету: `churn_risk` → `conflict` → `malfunction` → `prolonged` → `repeat` → `complaint`. Приоритет зафиксирован в `situation.ts` рядом со светофором, чтобы правило было одно на всё.

6. **Цитата — `<blockquote>`** (Telegram HTML). Визуально отделяет слова клиента от вывода системы. `splitMessage` не разрывает теги: алерт короткий, а в саммари цитат нет.

7. **Значки статусов обращений** — ✅ решено, 💬 есть ответ, ⏳ возможно без ответа, ❔ не определено. Легенда — одной строкой внизу отчёта вместо текущей длинной сноски.

## Риски / Компромиссы

- [Отчёт станет длиннее, потому что лимит обращений поднят до 20 и добавлены блоки обстановки] → Блоки вывода короткие (строка на чат или пункт), разбиение на части уже есть. Решающее для руководителя находится в первой части.
- [Светофор «краснеет» от любого всплеска, даже позитивного] → В причине пишем «всплеск активности», и руководитель видит, чем он вызван. Пороги уточним по обратной связи.
- [Дубли между «Требует решения» и разделом чата] → Это намеренно: первый блок — для оценки, раздел — для деталей.
- [Старые дайджесты без `headline` и `authorName` в инцидентах] → Рендер терпим к отсутствующим полям; пересборка периода в админке строит новую версию.

## План миграции

Схемы БД нет. После выката новые алерты и отчёты идут в новом формате, уже отправленные не меняются. Откат — возврат кода; дайджесты `digest-v3` старый код читает (лишнее поле игнорируется).
