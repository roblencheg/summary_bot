## Контекст

`ChatService.botMembershipChanged` уже переводит чат в статус `removed` при уходе бота и обратно при возврате (`server/services/chat-service.ts`). Подписки хранятся в `summary_subscriptions` / `alert_subscriptions` (таблицы `(recipient_id, chat_id)`) и читаются через `SubscriptionRepository`/`SubscriptionService`. Пикеры чатов для подписок (`subscription-matrix.tsx`, `ChatChecklist` в `user-details.tsx`) уже фильтруют по `status === 'active' || 'disabled'`, так что архивный чат нельзя назначить заново — но старые назначения, сделанные пока чат был живым, никуда не удаляются и продолжают тянуться в саммари и в проверку прав алертов.

Список `src/routes/chats.tsx` выводит все чаты одной таблицей без разделения — архивные перемешаны с рабочими.

## Цели / Не-цели

**Цели:**
- Удаление бота из чата сразу снимает все его подписки на саммари и алерты — чат не зависает в будущих рассылках.
- Архивные чаты не мешают работе со списком «Чаты», но остаются доступны для просмотра истории.
- Возврат бота восстанавливает статус чата, но не подписки — это решение администратора.

**Не-цели:**
- Не удаляем и не меняем исторические данные: сообщения, инциденты, отправленные алерты/отчёты.
- Не добавляем ручное «удаление навсегда» — не запрошено.
- Не меняем схему БД.

## Решения

1. **Снятие подписок — в `SubscriptionService`, а не в `ChatService` напрямую.** Новый метод `SubscriptionRepository.removeChatEverywhere(chatId)`: читает затронутых получателей по обоим видам подписки (для аудита), затем `DELETE FROM summary_subscriptions WHERE chat_id = ?` и `DELETE FROM alert_subscriptions WHERE chat_id = ?`. `SubscriptionService.purgeChat(chatId, actor)` вызывает репозиторий и пишет один аудит-лог `subscription.chat_archived` со списками затронутых получателей. Слой `route → service → repository` не нарушается: `ChatService` вызывает `SubscriptionService`, а не репозиторий подписок напрямую.

2. **Порядок сборки в `container.ts`.** `ChatService` теперь зависит от `SubscriptionService`, а `SubscriptionService` — от `ChatRepository` (не от `ChatService`), поэтому цикла нет. Нужно только переставить `subscriptions = new SubscriptionService(...)` выше `chats = new ChatService(...)` и передать `subscriptions` в конструктор `ChatService` последним параметром — остальные сервисы, которые сейчас получают `chats` и `subscriptions` по отдельности (`recipients`, `alerts`, `analysis`, …), не меняются.

3. **Вызов из `botMembershipChanged`.** После `this.repo.setStatus(chatId, 'removed')` добавляется `await this.subscriptions.purgeChat(chatId, 'telegram')` — симметрично существующему `await this.gaps.openBotRemoved(...)`. При возврате бота (`chat.status === 'removed'` → восстановление) подписки не трогаем: админ назначает их заново, как и для нового чата (требование «Отсутствие массовых назначений»).

4. **Вкладки в `chats.tsx`.** Простой локальный `useState<'active' | 'archive'>('active')`, фильтрация уже загруженного списка (`c.status === 'removed' || c.status === 'migrated'` → архив). Без изменений API: `/api/chats` отдаёт все чаты, как и раньше — это нужно другим страницам (`incidents`, `overview`, `alerts`), которые ищут чат по id в полном списке, чтобы показать название у исторических инцидентов архивного чата.

## Риски / Компромиссы

- [Удаление подписок необратимо через UI одним кликом] → Это ожидаемо: подписка — список на будущее, а не история; админ переназначит при необходимости, явно отражено сценарием.
- [Чат мигрировал (`migrated`), а не удалён — тоже архивный] → Уже так: `migrate()` переносит подписки на новый chat_id (существующая логика в `ChatRepository.migrate`), поэтому `purgeChat` вызывается только из ветки `removed`, не из `migrate`.
- [Между `setStatus('removed')` и `purgeChat` сервис может упасть] → SQLite без транзакций; если упадёт после смены статуса, но до снятия подписок, следующий `my_chat_member` (или ручная проверка) не триггернёт повтор. Приемлемо: строка подписки на архивный чат не рассылается — пикеры её не предлагают, а `summaryRecipients`/`alertRecipients` в худшем случае один раз пришлют пустой/устаревший раздел, что не хуже текущего поведения до этого изменения.

## План миграции

Схема не меняется, миграций нет. Деплой обычный: новый код просто начинает выполнять `purgeChat` при следующем событии `my_chat_member`; уже существующие «зависшие» подписки на давно архивные чаты можно почистить одной ручной командой после деплоя (разовый `DELETE ... WHERE chat_id IN (SELECT id FROM chats WHERE status IN ('removed','migrated'))` через `/db/exec`, если понадобится) — не часть кода, выполняется по желанию администратора.
