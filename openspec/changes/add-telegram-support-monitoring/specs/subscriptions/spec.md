## ADDED Requirements

### Requirement: Независимые подписки на саммари и алерты
Система SHALL хранить для каждого получателя отдельный список чатов для саммари и отдельный список чатов для алертов и MUST NOT выводить один из другого.

#### Scenario: Матрица A/B/C
- **WHEN** администратор назначает пользователю 1 саммари по чатам A и B, алерты только по B, а пользователю 2 — только саммари по C
- **THEN** пользователь 1 получает саммари с разделами A и B и алерты только по B, пользователь 2 — только саммари по C и никаких алертов

### Requirement: Настройки саммари получателя
Система SHALL позволять включать дневной и ночной отчёт для получателя по отдельности.

#### Scenario: Только утренний отчёт
- **WHEN** у получателя включён только ночной период
- **THEN** он получает отчёт в 08:00 и не получает в 22:00

### Requirement: Фильтры алертов получателя
Система SHALL позволять получателю (через администратора) выбрать категории алертов и минимальную серьёзность и MUST применять их поверх настроек чата.

#### Scenario: Фильтр по категории
- **WHEN** получатель подписан только на «Функциональный сбой», а в чате возник инцидент «Конфликт»
- **THEN** ему алерт не отправляется

#### Scenario: Фильтр по серьёзности
- **WHEN** минимальная серьёзность получателя «высокий», инцидент — «требует внимания»
- **THEN** ему алерт не отправляется

### Requirement: Валидация и подтверждение сохранения
Система SHALL проверять, что назначаются только существующие подключённые чаты и существующие категории, и MUST сообщать администратору о результате сохранения.

#### Scenario: Неизвестный чат
- **WHEN** запрос назначает несуществующий ID чата
- **THEN** система отвечает 422 и ничего не сохраняет

#### Scenario: Успешное сохранение
- **WHEN** администратор сохраняет корректную матрицу
- **THEN** интерфейс показывает подтверждение, изменение пишется в аудит со старым и новым значением

### Requirement: Повторная проверка прав перед отправкой
Система SHALL непосредственно перед отправкой каждого уведомления проверять текущие подписки получателя и MUST NOT раскрывать в нём чаты, доступ к которым отозван после постановки задания.

#### Scenario: Отзыв доступа к алертам
- **WHEN** алерт по чату B поставлен в очередь, затем администратор убрал B из alert-подписки получателя
- **THEN** алерт не отправляется, задание помечается «отменено: доступ отозван»

#### Scenario: Отзыв доступа к саммари
- **WHEN** перед отправкой саммари из подписки удалён чат A
- **THEN** отчёт собирается без раздела A и без упоминаний A в общих темах

### Requirement: Отсутствие массовых назначений
Система MUST NOT создавать подписки автоматически — ни при подключении чата, ни при активации получателя.

#### Scenario: Новый чат
- **WHEN** администратор активирует новый чат
- **THEN** ни один получатель не получает подписку на него без явного назначения
