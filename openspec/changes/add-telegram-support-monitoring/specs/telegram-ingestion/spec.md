## ADDED Requirements

### Requirement: Приём событий Telegram
Система SHALL получать события Bot API в режиме, заданном `TELEGRAM_MODE` (`polling` — по умолчанию в prod, `webhook`, `off` — по умолчанию в dev), и MUST сохранять сырое событие до его обработки, чтобы сбой обработки не терял данные.

#### Scenario: Обычное сообщение в группе
- **WHEN** участник подключённой группы пишет сообщение без упоминания бота, а у бота отключён privacy mode или есть права администратора
- **THEN** сообщение сохраняется и ставится в очередь анализа

#### Scenario: Режим приёма выключен
- **WHEN** `TELEGRAM_MODE=off` или не задан `TELEGRAM_BOT_TOKEN`
- **THEN** сервер работает, приём не запускается, обзор показывает «приём сообщений выключен»

#### Scenario: Webhook с неверным секретом
- **WHEN** на webhook приходит запрос без верного `X-Telegram-Bot-Api-Secret-Token`
- **THEN** система отвечает 401 и событие не сохраняется

#### Scenario: Long polling в prod
- **WHEN** prod-процесс стартует с режимом по умолчанию `polling`, а у токена установлен webhook
- **THEN** система снимает webhook без потери накопленных апдейтов и получает события через `getUpdates`

#### Scenario: Регистрация webhook при деплое
- **WHEN** prod-процесс стартует с `TELEGRAM_MODE=webhook`
- **THEN** система регистрирует webhook на `<PUBLIC_BASE_URL>/api/telegram/webhook` с секретом и показывает в обзоре состояние из `getWebhookInfo`

#### Scenario: Dev-контейнер с prod-токеном
- **WHEN** dev-процесс запущен с тем же `TELEGRAM_BOT_TOKEN` и режимом `off`
- **THEN** он не вызывает `setWebhook`, `deleteWebhook` и `getUpdates`, приём в prod не нарушается

### Requirement: Подключение чатов
Система SHALL автоматически регистрировать группу, в которую добавлен бот, со статусом «ожидает подключения» и MUST NOT собирать её сообщения в анализ, пока администратор не активирует чат.

#### Scenario: Бота добавили в новую группу
- **WHEN** приходит событие `my_chat_member` о добавлении бота в группу
- **THEN** чат появляется в разделе «Чаты» со статусом «ожидает подключения», названием, ID и типом

#### Scenario: Активация чата
- **WHEN** администратор активирует чат
- **THEN** система фиксирует дату старта сбора, проверяет права бота и privacy mode и показывает результат проверки

#### Scenario: Бот потерял права или удалён
- **WHEN** бота удаляют из чата или лишают прав
- **THEN** чат получает статус «бот удалён/нет прав», открывается пробел сбора по чату и отправляется техническое уведомление

#### Scenario: Личные сообщения и каналы
- **WHEN** событие пришло из канала или из личного диалога, не являющегося командой бота
- **THEN** система не сохраняет его как сообщение чата поддержки

### Requirement: Идемпотентное хранение сообщений
Система SHALL сохранять для каждого сообщения `chat_id`, `message_id`, время события и время получения в UTC, Telegram ID автора при наличии, отображаемое имя, username при наличии, текст или подпись, тип, `reply_to`, тему форума, признак редактирования и ссылку на источник, если её можно построить, и MUST использовать `chat_id + message_id` как ключ уникальности.

#### Scenario: Повторная доставка события
- **WHEN** Telegram повторно присылает то же сообщение
- **THEN** в БД остаётся одна запись сообщения

#### Scenario: Ссылка в приватной группе
- **WHEN** сообщение пришло из обычной группы без username, для которой ссылку построить нельзя
- **THEN** ссылка не выдумывается, хранятся название чата и ID сообщения

### Requirement: Редакции сообщений
Система SHALL сохранять каждое изменение текста как отдельную редакцию и MUST ставить сообщение на повторный анализ при существенном изменении текста.

#### Scenario: Существенная правка
- **WHEN** автор меняет «заказ пришёл» на «заказ не пришёл, жду третий день»
- **THEN** сохраняется редакция с прежним и новым текстом, сообщение анализируется повторно

#### Scenario: Правка опечатки
- **WHEN** правка меняет одну букву без изменения чисел
- **THEN** редакция сохраняется, повторный анализ не запускается

#### Scenario: Удаление сообщения
- **WHEN** участник удаляет сообщение в Telegram
- **THEN** система не обещает и не показывает обработку удаления, так как Bot API не присылает такие события

### Requirement: Роли и идентификация авторов
Система SHALL различать сотрудников поддержки по настраиваемому для чата списку Telegram ID и MUST NOT назначать роль, если автор в списке не указан.

#### Scenario: Сотрудник поддержки
- **WHEN** пишет пользователь из списка сотрудников чата
- **THEN** сообщение помечается как ответ поддержки

#### Scenario: Сообщение от имени чата
- **WHEN** сообщение отправлено от имени канала или анонимного администратора
- **THEN** показывается доступное имя с пометкой «идентификация ограничена»

### Requirement: Вложения без текста
Система SHALL учитывать вложения без текста в объёме сообщений, помечать их «содержимое не анализировалось» и MUST NOT делать выводов об их содержании.

#### Scenario: Фото без подписи
- **WHEN** приходит фото без подписи
- **THEN** оно учитывается в количестве сообщений и не передаётся в AI как содержательный текст

### Requirement: Пробелы сбора
Система SHALL фиксировать интервалы, когда сбор был недоступен (простой сервиса, ошибки получения событий, удаление бота), и MUST различать «сообщений не было» и «данные неполные».

#### Scenario: Простой сервиса
- **WHEN** сервер не работал 40 минут и после старта Telegram не вернул события этого интервала
- **THEN** в обзоре и в отчётах за период показывается «данные неполные» с интервалом недоступности

#### Scenario: Тихий чат
- **WHEN** сбор работал весь период, а сообщений не было
- **THEN** чат показывается с пометкой «сообщений не было», без признака сбоя
