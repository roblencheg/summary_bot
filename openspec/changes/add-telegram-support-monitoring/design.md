## Контекст

Проект: Node.js 24, Fastify, React, Rsbuild, SQLite и локальное файловое хранилище. AI вызывается через внешний Responses API. Слои: route → service → repository.

Ограничения среды, определяющие решения:

- **SQLite**: локальная БД в WAL-режиме, сохраняемая в DATA_DIR; сервис рассчитан на один процесс.
- **Деплой — один контейнер**, `scripts/start.sh` поднимает один процесс. Отдельного брокера очередей, cron-сервиса и Redis нет. dev-БД у каждого участника своя, prod — общая.
- **Публичный URL** задаётся пользователем в PUBLIC_BASE_URL; серверу нужен исходящий HTTPS к API подключённых интеграций.
- **Нет существующей системы идентификации** — админ-авторизацию делаем сами.

Требования к поведению — в `specs/**`. Здесь — как.

## Цели / Не-цели

**Цели:**
- Вертикальный сценарий «чат → сообщение → анализ → персональный алерт → журнал» за ≤60 с при штатной работе.
- Саммари 08:00/22:00 Новосибирска с доставкой ≤5 мин после границы.
- Устойчивость к рестарту, сбою AI и rate limit без потери принятых сообщений.
- Жёсткое разграничение: получатель видит только свои чаты, независимо для саммари и алертов.
- Всё, что ТЗ называет «рабочими решениями пилота», — настраиваемо из интерфейса.

**Не-цели:**
- Ответы в чатах, модерация, CRM/Трекер, личные переписки, каналы, user-аккаунты (MTProto).
- OCR, транскрибация, разбор файлов; загрузка истории до подключения бота (Bot API её не даёт).
- Межчатовые инциденты (ТЗ §8: для MVP — отдельные по чатам). Общие темы между чатами в саммари — да, только среди разрешённых получателю.
- Горизонтальное масштабирование на несколько процессов (lease-механизм это допускает, но не проверяется).
- Сбор размеченного датасета и нагрузочный прогон на реальном потоке — делает человек вместе с ответственным за пилот; код даёт инструменты.

## Решения

### 1. Почему не по образцу `notes` целиком

Образец покрывает синхронный CRUD. Здесь основная работа — фоновая: приём событий, очереди, планировщик, исходящие вызовы Telegram и AI. Поэтому добавляются два слоя, которых нет в шаблоне:

```
server/
  integrations/   telegram-client.ts, ai-client.ts   — внешние API, без БД и бизнес-правил
  workers/        poller.ts, analysis-worker.ts, scheduler.ts, delivery-worker.ts,
                  maintenance.ts, runner.ts          — циклы, вызывают только services
  domain/         periods.ts, masking.ts, spikes.ts, splitter.ts — чистые функции без I/O
```

Слои `route → service → repository` и zod-контракт для HTTP остаются обязательными. Воркер — это «транспорт» наравне с route: не выполняет SQL, вызывает сервисы. Схема ответа AI — zod, но в `server/integrations/ai-schemas.ts` (это не контракт HTTP API, в `shared/` ей не место).

### 2. Приём Telegram: webhook в prod, polling — для отдельного тестового бота

- `TELEGRAM_MODE=webhook|polling|off`. По умолчанию: `webhook` в prod, `off` в dev.
- **Prod — webhook** на `https://summary.example.com/api/telegram/webhook` (адрес задаётся env `PUBLIC_BASE_URL`, по умолчанию — этот домен). Почему webhook, а не polling: публичный HTTPS-домен деплоя есть, события приходят сразу (минимальная задержка для 60-секундного алерта), нет постоянного long poll-соединения.
- **Регистрация**: при старте prod-процесс вызывает `setWebhook` с `url`, `secret_token`, `allowed_updates`, `drop_pending_updates=false`, затем сверяет `getWebhookInfo` (url, `last_error_message`, `pending_update_count`) и показывает результат в обзоре. `deleteWebhook` вызывается только явным действием администратора.
- **Секрет webhook**: если `TELEGRAM_WEBHOOK_SECRET` не задан, он детерминированно выводится как `HMAC-SHA256("telegram-webhook", TELEGRAM_BOT_TOKEN)` в hex (допустимые символы и длина `secret_token` соблюдены) — отдельный секрет заводить не обязательно, а при смене токена секрет меняется сам. Проверка — заголовок `X-Telegram-Bot-Api-Secret-Token` сравнением за постоянное время.
- **Ответ webhook-у**: роут только сохраняет сырое событие (`telegram_updates`, `UNIQUE(update_id)`) и сразу отвечает 200; нормализация и анализ — асинхронно через очередь. Если сохранение не удалось — 500, Telegram повторит доставку (он хранит неполученные апдейты до 24 ч). Повторная доставка того же `update_id` не создаёт дублей.
- **Разработка**: используйте отдельный тестовый бот. В development приём по умолчанию выключен, чтобы исключить конфликт polling/webhook.
- `allowed_updates`: `message`, `edited_message`, `my_chat_member`, `chat_member`, `callback_query`.
- **Сообщения**: `INSERT … ON CONFLICT(chat_id, message_id) DO NOTHING`. `edited_message` → строка в `message_revisions`, обновление текущего текста; повторный анализ, если нормализованный текст изменился больше порога (расстояние Левенштейна/длина > 0.15 или изменились числа).
- **Права и privacy mode** — проверяются при подключении и раз в час: `getMe` (`can_read_all_group_messages`), `getChatMember(bot)` (админ ли), `getChat` (форум, username, тип). Если privacy mode включён и бот не админ — чат помечается «видны только команды и ответы боту», это показывается в UI, нулевая активность не выдаётся за «сообщений не было».
- **Ссылки**: публичный чат — `https://t.me/<username>/<message_id>`; приватная супергруппа — `https://t.me/c/<-100-префикс снят>/<message_id>` (откроется только участникам); обычная группа — ссылки нет, показываются название чата и ID. Темы форума — `message_thread_id`.
- **Удаления** Bot API не доставляет — не обещаем.

### 3. Пробелы сбора

Таблица `collection_gaps(chat_id NULL, started_at, ended_at, reason)`:
- **Простой сервиса**: воркер раз в 30 с пишет `settings.heartbeat_at`. При старте, если с прошлого heartbeat прошло > 5 мин, пишется пробел `[heartbeat, now)` с причиной `service_down`. Telegram хранит неполученные апдейты до 24 ч — при коротком простое данные дособерутся, тогда пробел помечается `recovered=1` по факту получения апдейтов с датой внутри окна; при простое > 24 ч пробел остаётся.
- **Ошибки приёма**: в режиме webhook — `getWebhookInfo` раз в минуту; `last_error_date` новее 2 мин или `pending_update_count` растёт > 2 мин → пробел `intake_error`; в режиме polling — ошибки `getUpdates` подряд > 2 мин.
- **Бот удалён из чата / потерял права** (`my_chat_member`) → пробел по чату `bot_removed` до возвращения.
- Саммари за период, пересекающийся с незакрытым пробелом, получает статус «данные неполные» с указанием интервала.

### 4. Очереди на SQLite

Одна таблица `jobs(id, kind, dedup_key UNIQUE, payload JSON, status, run_at, attempts, max_attempts, lease_token, lease_until, last_error, created_at, updated_at)`; `kind` ∈ `analyze_batch`, `build_chat_period`, `build_report`, `deliver`, `incident_eval`, `maintenance`.

- **Захват без транзакций**: `UPDATE jobs SET status='running', lease_token=?, lease_until=? WHERE id=(SELECT id FROM jobs WHERE kind=? AND status IN('pending','retry') AND run_at<=? ORDER BY run_at LIMIT 1) AND status IN('pending','retry')` → затем `SELECT … WHERE lease_token=?`. Один statement атомарен в SQLite, поэтому два захватчика не получат одно задание.
- **Восстановление после рестарта**: задания с истёкшим `lease_until` возвращаются в `retry`.
- **Повторы**: `run_at = now + min(base·2^attempt, cap) · (0.5 + random·0.5)`; для Telegram 429 — `retry_after` из ответа.
- **Идемпотентность создания**: `dedup_key` (например `report:<recipient>:<period_type>:<start>:<end>:v<version>`) + `INSERT … ON CONFLICT DO NOTHING` исключает параллельное создание одинаковых отчётов.
- Воркеры — `setInterval`-циклы внутри основного процесса с паузой 1 с при пустой очереди; `runner.ts` стартует их после `app.listen` и останавливает по SIGTERM (дожидается текущего задания до 10 с).
- **Почему не BullMQ/Redis**: SQLite достаточно для очередей одного процесса; дополнительный Redis для такого развёртывания не требуется. Почему не in-memory: теряется при рестарте, нарушает ТЗ §10.

### 5. Время и периоды

- В БД — только UTC ISO-8601 с `Z`. Расчёт границ — чистая функция `domain/periods.ts` на `Intl.DateTimeFormat` с `timeZone` из настроек (по умолчанию `Asia/Novosibirsk`); от `TZ` сервера не зависит. Новосибирск сейчас без перехода на летнее время, но код через IANA корректен и при смене правил.
- Периоды полуоткрытые: `day = [08:00, 22:00)`, `night = [22:00 предыдущего дня, 08:00)`. В SQL — `sent_at >= ? AND sent_at < ?`.
- Планировщик каждые 15 с вычисляет последнюю закрывшуюся границу и создаёт `report_periods(period_type, starts_at, ends_at) UNIQUE` и задания отчётов (идемпотентно). После простоя создаёт все пропущенные периоды, но отправку ограничивает настройкой `catchup_max_reports` (по умолчанию 2 последних периода на получателя); более старые формируются и доступны в UI с пометкой «не отправлен: догоняющий лимит». Отправленные позже границы + 15 мин помечаются «отправлено с задержкой».

### 6. AI-анализ

- **Клиент**: `openai` SDK с `openaiConfig()` из `server/platform.ts`; модель по умолчанию `gpt-5.4-mini`, меняется в настройках. Responses API со `text.format: json_schema` (strict), схема генерируется из zod (`z.toJSONSchema`).
- **Пакеты**: сообщения чата группируются debounce-окном 3 с (до 20 сообщений), чтобы связанные реплики анализировались вместе и соблюдалось ≤60 с. В запрос передаётся: правила (системный промпт, версия), контекст — до 30 предыдущих сообщений чата за окно контекста (по умолчанию 24 ч) + цепочка `reply_to`, открытые инциденты чата (id, краткая суть, сущности), роли авторов (сотрудник/участник/неизвестно). Контекст помечен как контекст и не анализируется повторно.
- **Защита от инструкций в сообщениях**: тексты передаются только как JSON-данные в user-сообщении внутри явного блока «данные чата», системный промпт фиксирован в коде и прямо требует игнорировать инструкции из данных. Ответ модели влияет только на поля схемы; адресаты, права и правила вычисляются кодом и от ответа не зависят.
- **Схема ответа на сообщение**: `message_id`, `is_request`, `request_key` (объединение сообщений одного обращения), `topic` (из настраиваемого справочника + `other`), `summary` (кратко, без домыслов), `tone` (`neutral|positive|negative|mixed`), `categories[]` (7 категорий), `severity` (`info|attention|high|critical`), `severity_reason`, `confidence` (0–1), `repeat_markers` («третий раз», «третий день»…), `entities` (номера заказов и т.п. — для различения проблем), `incident_ref` (`new` | id открытого инцидента | `none`), `resolution_confirmed` (только при явном подтверждении), `support_reply_to[]`, `evidence_message_ids[]`.
- **Валидация**: zod-парсинг; `evidence_message_ids` и `incident_ref` обязаны входить в переданный набор — иначе поле отбрасывается и ставится флаг `invalid_refs`; неизвестный `topic` → `other`. Невалидный ответ → повтор задания, после 3 — `analysis_status='failed'` и видимость в UI.
- **Версии**: в `analysis_results` — `model`, `prompt_version`, `rules_version` (хэш настроек правил), `analyzed_at`, токены.
- **Сбой AI**: приём не зависит от анализа. Задания остаются в очереди с backoff, обзор показывает отставание (самое старое непроанализированное сообщение). Ключевые слова как подмена анализа не используются; алерты по неанализированным сообщениям не шлются, всплеск (чисто количественный) — шлётся с пометкой «тематика не проанализирована».
- **Почему один вызов на пакет, а не на сообщение**: повторяемость и связь реплик видны только в контексте; дешевле по токенам.

### 7. Инциденты, повторяемость, дедупликация

- **Решение «к какому инциденту»** даёт модель (`incident_ref`), код проверяет ограничения: тот же чат; разные `entities` одного типа (два разных номера заказа) → объединение запрещено, создаётся новый инцидент; закрытые/помеченные «ложный» администратором инциденты не переоткрываются автоматически — новое событие создаёт новый инцидент со ссылкой `related_incident_id` (аудит сохраняется).
- **Повторяемость** считается кодом по `incident_messages` (SQL-агрегаты в репозитории): ≥ N связанных сообщений за M минут (3/30), повтор того же автора по нерешённой проблеме за 24 ч, явный маркер «третий раз/день» — самостоятельное основание. Разные авторы → `affected_authors`; различие «повтор одного» и «массовая» — по `COUNT(DISTINCT author_id)`.
- **Решение об уведомлении** (`IncidentService.evaluate`) — чистая функция от состояния инцидента и настроек: новый инцидент выше порогов → алерт; повтор в cooldown (15 мин) → только счётчик; рост серьёзности, новая категория, рост `affected_authors` в ≥2 раза или новый существенный факт (флаг модели `material_update`) → немедленное обновление; после cooldown при новых данных → одно сводное обновление. Независимый инцидент имеет свой cooldown и не подавляется.
- **Пороги получателя**: инцидент уходит получателю, если чат в его alert-подписке, категория в его выбранных категориях, серьёзность ≥ его минимума и ≥ минимума чата, уверенность ≥ порога чата. Ниже порога уверенности, но с серьёзностью ≥ `attention` — «пограничный», виден в UI для проверки, не рассылается.

### 8. Всплески

- Источник — `messages` (SQL `COUNT`, `COUNT(DISTINCT author_key)` по окну) в `MessageRepository`, считается после каждого принятого пакета и раз в минуту.
- Условие: в скользящем окне `W` (5 мин) `count ≥ min_abs` (20) **и** `count ≥ k · baseline` (3×). `baseline` = среднее число сообщений на окно `W` в тот же локальный час суток за предыдущие 7 дней, **включая окна без активности** (иначе база завышается), **исключая текущее окно и уже идущий всплеск**. Если с начала сбора по чату < 7 дней или есть пробелы в истории > 20% — режим «накопление истории»: только абсолютный порог, в алерте пометка «ограниченная база сравнения».
- Массовое обсуждение: ≥ 5 разных авторов за 10 мин в рамках одного инцидента — повышение до категории «повторяющаяся ситуация/массовая».
- Всплеск — отдельный инцидент категории «всплеск активности» с `tone` из анализа сообщений окна; негатив не приписывается, если анализ его не показал.

### 9. Саммари

- **Двухуровневая сборка** (из-за прав и больших чатов): `chat_period_digests(chat_id, period_id, version)` — общий для всех получателей разбор чата за период; персональный отчёт собирается **в момент отправки** из дайджестов чатов, разрешённых получателю **сейчас** (повторная проверка прав, ТЗ §9/кейс 17).
- **Числа — кодом** (SQL в репозиториях): сообщения, уникальные авторы (по `author_id`, иначе по `sender_chat_id`; скрытые авторы считаются отдельной строкой «неидентифицированные»), обращения (`COUNT(DISTINCT request_key)`), повторные обращения, сигналы риска, распределение тона, темы с долей среди классифицированных + «прочее/не определено», всплески, обращения без признака ответа (нет сообщения сотрудника в reply-цепочке/после него в течение `no_reply_window`, по умолчанию 30 мин), вложения без текста.
- **Текстовая часть — AI** только для «краткой картины» и формулировок тем, с иерархической агрегацией: если сообщений в периоде > 300, чат режется на пакеты по времени с перекрытием 10 сообщений (не теряются события на границах), по каждому — частичный разбор, затем свёртка. Каждое утверждение несёт `evidence_message_ids`; утверждения без валидных оснований отбрасываются при сборке.
- **Ранжирование** обращений: серьёзность → повторы → число затронутых → время; в Telegram до 10, с пометкой «выборка, полный список — в веб-интерфейсе».
- **Маскирование** (`domain/masking.ts`): телефоны, номера заказов/ID вида `\d{3}-\d{7}`, номера карт, e-mail → `007-62•••83`. Применяется при рендеринге уведомлений; исходник — в UI админу.
- **Разбиение**: лимит Telegram 4096 символов; режем по границам разделов/абзацев, не внутри HTML-тега и ссылки; каждая часть получает «Часть i/n»; отправка строго последовательно, следующая часть — только после успеха предыдущей.
- **Версия формирования** входит в ключ отчёта; ручной запуск создаёт новую версию с флагом `manual`.

### 10. Доставка

- `delivery_jobs` (получатель, тип: `alert|incident_update|summary|test|tech`, ссылка на отчёт/инцидент, части) + `delivery_attempts` (время, HTTP-код, `error_code`, описание, `telegram_message_id`).
- Перед отправкой: получатель активен и привязан; права на все чаты содержимого действительны → иначе задание `cancelled_access_revoked` (алерт) или пересборка из дайджестов (саммари).
- **Ошибки**: 403 (бот заблокирован / не начат диалог) → `blocked`, без повторов, получатель помечается; 400 «chat not found» — аналогично; 429 → повтор через `retry_after`; 5xx/сеть → backoff до 5 попыток.
- **Неопределённый результат** (таймаут после отправки запроса): попытка помечается `uncertain`; политика — **at-least-once**: повторяем с пометкой «повтор: возможен дубль» в тексте. Exactly-once не обещаем; задокументировано в README.
- **Rate limit**: глобальный токен-бакет 25 сообщений/с, 1 сообщение/с на получателя.
- Успех = «принято Telegram API», не «прочитано».

### 11. Авторизация администратора

- Таблицы `admins(login, password_hash scrypt, role)` и `admin_sessions(token_hash, admin_id, expires_at)`; cookie `sid` `httpOnly; Secure (prod); SameSite=Strict`, TTL 12 ч, скользящее продление. Разрешённый `Origin` и CORS — `PUBLIC_BASE_URL` (`https://summary.example.com`); в dev — origin превью.
- Первый админ — из секретов `ADMIN_INITIAL_LOGIN`/`ADMIN_INITIAL_PASSWORD` при пустой таблице `admins`; далее админы управляются в UI.
- Fastify-хук `preHandler` на всех `/api/*`, кроме `/api/auth/login`, `/api/health`, `/api/ready`, `/api/telegram/webhook/*`. Изменяющие запросы дополнительно проверяют `Origin` (CSRF). Брутфорс: 5 неудачных попыток → блок логина на 15 мин.
- **Почему не Telegram Login Widget**: требует привязки домена у BotFather и публичного домена — не гарантировано.

### 12. Конфигурация и аудит

- `settings(key, value JSON, updated_at, updated_by)` — глобальные; `chat_rules(chat_id, …)` — переопределения по чату. Значения по умолчанию — в коде (`server/services/settings-defaults.ts`), документированы в `docs/admin-guide.md`.
- `audit_log(actor, action, entity, entity_id, old_value, new_value, at)` пишет каждый сервис изменения прав, подписок, правил, статусов инцидентов, админов; секреты в настройках не хранятся вовсе.

### 13. Хранение, удаление, резервные копии

- Ежесуточно (`maintenance`): удаление сообщений и ревизий старше 90 дн, результатов анализа к ним, отчётов/инцидентов старше 180 дн, технических записей (`delivery_attempts`, `jobs` завершённые, `telegram_updates`) старше 30 дн. Порядок удаления — от зависимых к родителям, пакетами по 500 через `DELETE … WHERE rowid IN (SELECT … LIMIT 500)`; векторных индексов нет. После крупной очистки — `/db/vacuum`.
- Инциденты, пережившие свои сообщения, сохраняют краткую суть и счётчики, ссылки на удалённые сообщения помечаются «источник удалён по сроку хранения».
- **Бэкап**: ежедневный экспорт таблиц в NDJSON.gz в локальное хранилище (`backups/<date>/<table>.ndjson.gz`), ротация копий и восстановление скриптом scripts/restore.ts. Полный volume копируют при остановленном сервисе.

### 14. Метрики и здоровье

- `/api/health` — процесс жив; `/api/ready` — БД отвечает, воркеры шлют heartbeat < 60 с, Telegram `getMe` < 5 мин назад успешен.
- Метрики считаются SQL-агрегатами по существующим таблицам: задержки (`received_at − sent_at` — задержка Telegram, `analyzed_at − received_at`, `delivered_at − триггер`), размеры очередей, ошибки, сообщения/инциденты/повторы, токены AI (из `analysis_results`), доля «ложное срабатывание» в feedback.
- Технические уведомления (`tech`) — получателям с флагом `is_tech_admin`: AI недоступен > 10 мин, ошибки приёма (webhook/polling) > 2 мин, бот удалён из чата, очередь доставки > 15 мин, отказ миграции не покрывается (процесс не стартует — видно в логах сервиса). Дедуп технических уведомлений — 1 раз в 30 мин на тип.

### 15. Дизайн тестов (ожидает разрешения, см. AGENTS.md)

Автотесты в проект пока **не** добавляются. Предлагаемый дизайн для запроса разрешения:
- `vitest`, только чистые функции `server/domain/*` и `IncidentService.evaluate` с фейковым репозиторием: границы периодов (07:59:59.999/08:00/21:59/22:00, смена даты, `TZ=UTC` процесса), разбиение 4096, маскирование, всплеск/накопление истории, cooldown-сценарии кейсов 11–12, фильтр прав получателя (кейсы 3, 17).
- Интеграционный прогон на dev-БД: дубль апдейта и редакция (кейс 2), рестарт с незавершённым lease (кейс 16).
- Eval-скрипт `scripts/eval-alerts.ts` (не тест, инструмент калибровки): прогоняет размеченный JSONL через анализ, считает confusion matrix по категориям, полноту/точность; три примера заказчика и отрицательные кейсы — обязательный набор. Размеченные ≥100 примеров собирает человек с ответственным за пилот; настроечная и проверочная выборки разделяются по `dialog_id`.

## Отклонения при реализации

Найдены при реализации и проверке на тестовом окружении, решения ниже заменяют исходные:

- **Очереди без общей таблицы `jobs`.** Доменные таблицы хранят статусы заданий и lease (`lease_token`, `lease_until`):
  - `telegram_updates.status` — приём;
  - `messages.analysis_status` — анализ;
  - `report_periods.status` — периоды;
  - `delivery_jobs.status` — доставка.

  Отдельная таблица заданий удваивала бы число запросов. Захват: `UPDATE … SET lease_token=? WHERE id IN (SELECT … LIMIT n)`, затем `SELECT … WHERE lease_token=?`. Идемпотентность — уникальные ключи (`update_id`, `chat_id+message_id`, `dedup_key`, ключ отчёта).
- **`lastInsertRowid` ненадёжен при `changes=0`.** Решения принимаются по `changes`, id перечитывается.
- **Иерархическая агрегация саммари** — по уже размеченным обращениям, а не по нарезке сырых сообщений. Цепочка: сообщение (анализ) → обращение (краткая суть) → чат за период (до 150 обращений и инциденты в один вызов модели) → отчёт получателя (код). События на границах не теряются: анализ идёт по сообщениям, период режется SQL-ом. Основания утверждений проверяются по сообщениям периода.
- **Ключ обращения привязан к автору.** Модель склеивала одинаковые жалобы разных авторов в одно обращение. Теперь разные авторы — всегда разные обращения, а общую проблему связывает инцидент. Промпт `analysis-v2`.
- **Категории и минимальная серьёзность алертов** — колонки `recipients` вместо отдельной таблицы (один список на получателя).
- **Миграция группы в супергруппу** (`migrate_to_chat_id`): настройки, сотрудники и подписки переносятся на новый ID.
- **Недоставленное саммари** (получатель не активирован или заблокирован) всё равно собирается по текущим правам и доступно в интерфейсе со статусом «отменён».
- **Prod по умолчанию — long polling, а не webhook.** После первого деплоя Telegram не смог доставить webhook на домен деплоя: `getWebhookInfo` — «Connection timed out», 2 апдейта в очереди; изнутри домен отвечал за 0,3 с. Входящие соединения от Telegram до хостинга не проходят, исходящие к `api.telegram.org` работают. В режиме `polling` prod при старте снимает webhook (`drop_pending_updates=false`) и забирает события через `getUpdates`. Webhook остаётся опцией `TELEGRAM_MODE=webhook`.
- **Readiness** учитывает ожидаемый интервал каждого воркера: у обслуживания — часы, у доставки — 60 с.

## Риски / Компромиссы

- [Каждый SQL — HTTP round-trip, 20–80 мс] → пакетные `INSERT` из нескольких VALUES, кэш настроек и подписок в памяти с инвалидацией при изменении, агрегаты одним запросом.
- [Нет транзакций: частично записанное состояние при падении] → порядок «сначала факт, потом производное», идемпотентные ключи, задания пересчитывают производное заново.
- [Один процесс: долгий AI-вызов блокирует цикл] → воркеры асинхронные и независимые, таймаут AI 30 с, параллелизм анализа 3.
- [Privacy mode включён — бот не видит обычные сообщения] → проверка при подключении, предупреждение в UI, инструкция в README (сделать бота админом или `/setprivacy → Disable` до добавления в чат).
- [Лимит БД 1 ГиБ при больших чатах] → сроки хранения, хранение только текста, мониторинг размера в обзоре.
- [Качество AI не доказано до разметки] → пилот с порогами по умолчанию, обратная связь «полезно/ложно», eval-скрипт; целевые 90%/80% подтверждаются только на независимой выборке.
- [Дубль уведомления при неопределённом результате] → at-least-once с явной пометкой повтора; документировано.
- [Ссылки `t.me/c/…` открываются только участникам чата] → дополнительно показываем название чата и ID сообщения.
- [Один токен используется несколькими процессами] → отдельные боты для разработки и production; один потребитель polling на токен.
- [Privacy mode: на 21.10.2026 у `@nlintchatbot` `can_read_all_group_messages=false`] → до добавления бота в чаты выполнить в @BotFather `/setprivacy → Disable` (или назначать бота администратором группы); если бот уже был в группе — удалить и добавить заново; UI предупреждает по `getMe`/`getChatMember`.

## План миграции

1. Выкат только расширяет схему (`CREATE TABLE IF NOT EXISTS`), шаблонная таблица `notes` остаётся нетронутой.
2. Секреты `TELEGRAM_BOT_TOKEN`, `ADMIN_INITIAL_LOGIN`, `ADMIN_INITIAL_PASSWORD` уже заданы в дашборде (21.10.2026). Без токена сервис стартует, UI показывает «бот не настроен», приём не запускается. Первый prod-деплой регистрирует webhook.
3. Пилот: администратор вручную подключает выбранные чаты и тестовых получателей; массовых назначений код не создаёт.
4. Откат: остановка приёма (`TELEGRAM_MODE=off`) и деплой предыдущей ревизии; данные остаются.

## Открытые вопросы

- Кто тестовые получатели и технический администратор пилота — назначает администратор в UI.
