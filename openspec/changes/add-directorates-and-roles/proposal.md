# Этап Б: дирекции, руководители и суперадмин

## Why

Сейчас в системе одна роль — администратор с полным доступом. Руководителям подразделений нужно самостоятельно и монопольно вести свои чаты: подключать их, назначать получателей саммари и алертов, настраивать правила — и не видеть чужие чаты. Глобальные настройки системы должны остаться только у суперадмина (суперадминистратор). Все текущие чаты и получатели относятся к основного подразделения (руководитель — руководитель подразделения); для них ничего не должно измениться.

Это второй этап из трёх. Этап А (отчёты без шума, настройки инцидентов в Telegram) реализован; этап В — важность чатов и «тихие» чаты в саммари — опирается на дирекции из этого этапа.

## What Changes

- **Дирекции.** Новая сущность: название, сколько угодно руководителей. Чат принадлежит одной дирекции-владельцу; суперадмин может дать доступ на чтение к чату другим дирекциям. Получатель может состоять в нескольких дирекциях.
- **Роли:**
  - **суперадмин** — всё, что есть сейчас: глобальные настройки, аудит, журнал отправок, периоды, администраторы; плюс новый раздел «Дирекции» (создание дирекций, руководителей, доступ дирекций к чатам, «Неразобранные» чаты);
  - **руководитель** — облегчённый интерфейс: «Обзор», «Чаты», «Пользователи», «Инциденты», «Отчёты», правила чатов (пороги, категории). Видит только чаты своих дирекций и получателей своих дирекций. Глобальных настроек, аудита и журнала отправок у него нет.
- **Подключение своего чата руководителем.** Кнопка «Подключить чат» выдаёт одноразовую ссылку `https://t.me/<бот>?startgroup=<код>` (24 часа). Руководитель добавляет по ней бота в группу — чат закрепляется за его дирекцией. Код можно ввести и вручную в группе: `/connect <код>`. Чат с владельцем чужим кодом не перехватить; сменить владельца может только суперадмин.
- **Чат без кода** (бота добавили просто так) попадает в «Неразобранные» — его видит только суперадмин и назначает дирекцию.
- **Перенос текущих данных — без изменений для пользователей.** При первом запуске создаётся «Основное подразделение»; все существующие чаты становятся её чатами, все существующие получатели — её получателями, все существующие учётные записи администраторов — суперадминами. Подписки, отчёты, алерты, меню бота — без изменений. Учётную запись руководителя для руководителя подразделения создаёт суперадминистратор в разделе «Дирекции» (пароль задаёт он, система паролей не придумывает).
- **Ограничения проверяет сервер:** каждый запрос руководителя фильтруется по его дирекциям; чужой чат, инцидент, получатель или отчёт → 404.
- **Подписки получателя у руководителя** — только по видимым ему чатам; сохранение матрицы не трогает подписки получателя на чаты других дирекций.
- **Один человек в нескольких дирекциях.** Если руководитель создал получателя, а этот Telegram-аккаунт уже привязан к получателю другой дирекции, при привязке записи объединяются: человек остаётся одним получателем, состоящим в обеих дирекциях, и получает рассылки по чатам обеих. **BREAKING** для текущего поведения: раньше такая привязка отклонялась («Telegram ID уже занят»).
- **Чат, подключённый по ссылке руководителя, сразу активен.** Сбор сообщений и права бота проверяются автоматически в момент подключения — без отдельного нажатия «Активировать сбор». Чаты, подключённые без кода (неразобранные), активируются вручную, как и сейчас.
- **Отчёты в интерфейсе руководителя** — показываются целиком, как в Telegram, включая все разделы отчёта. Если получатель состоит в нескольких дирекциях, руководитель видит отчёт полностью, а не только разделы своих чатов — это осознанное решение ради простоты первой версии.

## Capabilities

### New Capabilities
- `directorates`: дирекции, роли руководителя и суперадмина, доступ дирекций к чатам, подключение чата по коду, неразобранные чаты, перенос текущих данных в основное подразделение, серверная фильтрация по дирекциям.

### Modified Capabilities
- `admin-auth`: «Проверка прав на backend» — кроме сессии, проверяется роль и дирекции.
- `admin-console`: «Разделы веб-интерфейса» — набор разделов зависит от роли.
- `recipient-binding`: «Привязка по одноразовому коду» — объединение с уже привязанным получателем другой дирекции.
- `telegram-ingestion`: «Подключение чатов» — закрепление по коду, неразобранные чаты.
- `subscriptions`: «Валидация и подтверждение сохранения» — руководитель назначает только видимые ему чаты, чужие подписки не трогаются.

## Impact

- Схема БД (только добавление): `directorates`, `admin_directorates`, `chat_directorates`, `recipient_directorates`, `chat_claim_codes`, колонка `admins.role` (по умолчанию `superadmin` — все текущие учётки становятся суперадминами без отдельного шага). Одноразовый перенос данных в основное подразделение с маркером выполнения.
- Сервер: новый `AccessService` (scope запроса), `DirectorateService` + репозитории; scope передаётся в сервисы чатов, получателей, подписок, инцидентов, отчётов и обзора; новые эндпоинты `/api/directorates/*`, `/api/chats/claim-link`; `BotCommandService` — `/start <код>` и `/connect <код>` в группе.
- Фронтенд: роль в `/api/auth/me`, навигация по роли, раздел «Дирекции» для суперадмина, кнопка «Подключить чат» у руководителя, скрытие глобальных действий.
- Документация: `docs/project.md`, `docs/admin-guide.md` (роли, подключение чата руководителем).
- Деплой без остановки: миграции только добавляют таблицы и колонку; до создания учётки руководителя всё работает как сейчас.
