## Контекст

Сейчас одна роль: любой вошедший администратор (`admins`) видит и меняет всё. Сессия кладёт в `req.admin` учётку, маршруты вызывают сервисы без контекста доступа. Чаты, получатели и подписки глобальные. Получатель уникален по `telegram_user_id`; повторная привязка того же Telegram ID к другому получателю отклоняется (`reason: 'taken'`). Managed SQLite без транзакций, ≈160 мс на запрос, schema через `applySchema()` (только `CREATE TABLE IF NOT EXISTS` и `ALTER TABLE ADD COLUMN` с проверкой).

## Цели / Не-цели

**Цели:** изоляция руководителей по дирекциям на сервере; подключение чата руководителем без участия суперадмина; нулевые изменения для текущих пользователей; деплой без простоя.

**Не-цели:** важность чатов и «тихие» чаты (этап В); раздельные расписания саммари по дирекциям (у получателя одно расписание и одни фильтры алертов на все дирекции); вход руководителя через Telegram.

## Решения

1. **Модель данных (только добавление).**
   - `directorates(id, name UNIQUE, created_at)`.
   - `admins.role TEXT NOT NULL DEFAULT 'superadmin'` — существующие учётки становятся суперадминами сами, без шага миграции. Новые руководители создаются с `role = 'manager'`.
   - `admin_directorates(admin_id, directorate_id, PK)`.
   - `chat_directorates(chat_id, directorate_id, access TEXT 'owner'|'reader', created_at, PK(chat_id, directorate_id))` + уникальный индекс `(chat_id) WHERE access = 'owner'` — у чата не больше одного владельца.
   - `recipient_directorates(recipient_id, directorate_id, PK)`.
   - `chat_claim_codes(code_hash PK, directorate_id, created_by, expires_at, used_at, chat_id)` — как `binding_codes`.
   Почему не `chats.directorate_id`: нужна ещё и выдача доступа на чтение другим дирекциям — одна таблица связей покрывает оба случая.

2. **Одноразовый перенос в основное подразделение.** В `applySchema()` после создания таблиц: если в `settings` нет ключа `migration.directorates_v1`, создать «основное подразделение» (`INSERT … ON CONFLICT DO NOTHING`), вставить `chat_directorates(owner)` для всех чатов, `recipient_directorates` для всех получателей (`INSERT … SELECT … ON CONFLICT DO NOTHING`), затем записать маркер. Без транзакций шаги идемпотентны: при падении посередине повторный запуск доделает их. Маркер нужен, чтобы чаты, добавленные позже без кода, не попадали в основное подразделение автоматически.
   Учётку руководителя для руководителя подразделения перенос не создаёт: пароль задаёт суперадмин.

3. **Scope запроса — `AccessService`.** После аутентификации строится `Scope = { kind: 'super' } | { kind: 'manager', directorateIds, chatIds (видимые), ownedChatIds, recipientIds }` — 3 SQL-запроса на запрос руководителя (для суперадмина — ни одного). Хелперы: `requireSuper(req)`, `assertChat(scope, id, 'read'|'own')`, `assertRecipient(scope, id)`; невидимое → `NotFoundError` (404), действие владельца без права → `ForbiddenError` (403).
   Маршруты передают `scope` в сервисы, сервисы — в репозитории фильтр `chat_id IN (…)` / `recipient_id IN (…)`. Для суперадмина фильтр не применяется — его запросы выполняются как сейчас.
   Почему не фильтровать на клиенте: изоляция — требование безопасности, только сервер.
   Почему список id, а не JOIN в каждом SQL: у руководителя десятки чатов, `IN` по ним дешевле и не требует переписывать все запросы на JOIN с таблицами доступа.

4. **Эндпоинты только для суперадмина** (`requireSuper`): `/api/settings*`, `/api/audit`, `/api/deliveries*`, `/api/periods*`, `/api/admins*`, `/api/directorates*`, `POST /api/recipients/menu` (всем активным). Для руководителя `/api/chats` отдаёт только видимые, без неразобранных.

5. **Подключение чата по коду.** `POST /api/chats/claim-link` (руководитель, при нескольких дирекциях — `directorateId`) → `{ link, expiresAt }`. Telegram при добавлении по `?startgroup=` присылает в группу `/start@бот <код>`; команда видна боту и при включённом privacy mode. `BotCommandService` обрабатывает в группе `/start <код>` и `/connect <код>`: код валиден → если у чата нет владельца, вставить `chat_directorates(owner)`, погасить код, аудит, ответ в группе; если владелец есть — «Чат уже подключён» и аудит `chat.claim.rejected`. Порядок событий (`my_chat_member` раньше команды) не важен: чат регистрирует `seen()`.
   Закреплённый по коду чат **сразу переходит в `active`** (как после ручной активации) и проверяет права бота — руководитель, который сам добавил бота, уже хочет сбор; лишний клик не нужен. Чаты без кода (неразобранные) активирует вручную тот, кому их назначили — как и сейчас.

6. **Получатель в нескольких дирекциях и объединение при привязке.** Руководитель создаёт получателя → `recipient_directorates` с его дирекцией. При привязке, если Telegram ID уже у другого получателя X: перенести дирекции и подписки нового в X (`INSERT … SELECT … ON CONFLICT DO NOTHING`), погасить код, удалить новую запись (она pending, без истории доставок), аудит `recipient.bind.merged`. Удаление получателя руководителем, если тот состоит и в других дирекциях, — исключение из своей дирекции и снятие подписок на чаты, видимые только ей.

7. **Подписки в scope.** `SubscriptionService.replace(kind, recipientId, chatIds, actor, scope)`: проверка, что все `chatIds` ⊂ `scope.chatIds`; итог = (текущие подписки вне scope) ∪ новые. Для суперадмина — как сейчас.

8. **Отчёты у руководителя.** `GET /api/reports` — отчёты получателей его дирекций (видимость по получателю, не по чату); детали отдаются целиком, включая `parts` и `fullText`, как в Telegram — без урезания по чатам. Это сознательно упрощает первую версию: если получатель в нескольких дирекциях, оба руководителя видят один и тот же отправленный текст.

9. **Фронтенд.** `/api/auth/me` отдаёт `role` и `directorates`. Навигация и кнопки по роли: у руководителя скрыты «Саммари/Алерты» глобальные разделы (вместо них «Отчёты»), «Журнал отправок», «Настройки», «Аудит»; в «Чатах» — «Подключить чат» (модалка со ссылкой и кнопкой копирования). Новый раздел «Дирекции» у суперадмина: список дирекций, руководители (создать, пароль, отключить), чаты дирекции с типом доступа, «Неразобранные» с назначением владельца.

## Риски / Компромиссы

- [Пропущенная проверка scope в каком-то эндпоинте — утечка чужих данных] → Проверки централизованы в `AccessService`; по каждому маршруту — задача в tasks; ручная проверка учёткой руководителя чужих id по всем разделам.
- [Перенос упал посередине] → Все шаги идемпотентны, маркер пишется последним.
- [Объединение получателей ошибочно сольёт разных людей] → Объединение только по одному и тому же Telegram ID, подтверждённому кодом из личного диалога.
- [Расписание и фильтры алертов у получателя общие на все дирекции] → Осознанное упрощение; разные руководители меняют одни и те же настройки человека, изменения в аудите.
- [Рост числа SQL на запрос руководителя (+3)] → Приемлемо (≈0,5 с); при необходимости — кэш scope на время сессии с инвалидацией при изменении доступа.
- [Отчёт получателя из двух дирекций виден целиком обоим руководителям, включая чужие чаты] → Осознанный выбор ради простоты первой версии; если понадобится разделение, это отдельное последующее изменение.

## План миграции

1. Деплой: создаются таблицы и колонка, выполняется перенос в основное подразделение. Все текущие учётки — суперадмины, интерфейс у них не меняется, рассылки не меняются.
2. суперадминистратор в «Дирекциях» создаёт учётку руководителя для руководителя подразделения.
3. Откат: старый код игнорирует новые таблицы и колонку; данные не теряются.
