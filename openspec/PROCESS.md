# Процесс изменений (OpenSpec)

Этот файл лежит в проекте, значит проект ведётся по OpenSpec, и это **обязательный** способ работы — пока каталог `openspec/` есть в корне.

Что где лежит:

- `openspec/specs/<capability>/spec.md` — текущее поведение системы, источник правды о требованиях.
- `openspec/changes/<change-id>/` — незакрытое предложение: `proposal.md` (зачем), `specs/**` (дельты требований), `design.md` (как), `tasks.md` (шаги реализации).
- `openspec/changes/archive/` — принятые изменения.
- `openspec/config.yaml` и `openspec/schemas/` — настройки процесса. Руками не правь.

## Порядок работы

1. Прочитай `openspec/specs` — там текущее поведение системы.
2. Содержательное изменение начинай с навыка `openspec-propose`. Он готовит предложение и **останавливается**.
3. `openspec validate --all --strict` — после каждой правки артефактов, до зелёного. Без аргументов команда в неинтерактивном режиме ничего не проверяет и выходит с кодом 0.
4. Артефакты предложения **закоммить**: остановка касается только кода.
5. Реализацию (`openspec-apply-change`) и принятие в спеки (`openspec-archive-change`) запускает человек, не ты.
6. `openspec/specs/**` напрямую не редактируй — спеки меняются только через дельты. После архивации ещё раз прогони валидацию: главная спека, собранная из дельты, обязана иметь секции `## Purpose` и `## Requirements`.
7. Попался пункт задачи, который тебе закрывать нельзя (тесты без разрешения) или нечем (ручная проверка человеком) — не блокируйся: отметь отложенным, назови в отчёте, продолжай.
8. Опечатки и форматирование без изменения поведения — можно напрямую, без предложения.

## Если задача не ложится в заведённую архитектуру

Фоновая обработка, внешний API, другой способ хранения — не притягивай задачу к образцу силой. Опиши решение в `design.md` предложения и объясни, почему здесь иначе.
